# 学习搭子 v1.4：整片字幕的分层记忆

> 版本：v1.4（1.4.0），2026-11-08 合并到 main。实际落地和验证结果见 [CHANGELOG.md](../CHANGELOG.md)。
> 目标：AI 读完整部视频的字幕，既能粗略把握全片往哪走，又能比较精确地把握暂停点前后各 30 秒，最后把“这一段在说什么”讲准。

## 1. 现在的问题

v1.2 的字幕是**边播边记**：内容脚本盯着播放器的字幕节点，播到哪记到哪。v1.3 为了课程重点读了完整字幕，但求助时只在「暂停点附近没播过」时拿来补 ±30 秒。暂停求助时 AI 拿到的仍然只有：

- 暂停点**之前**、而且**真的播过**的 30 秒（v1.3 起没播过时能用完整字幕补）。
- 暂停点**之后**的 30 秒基本没有。很多时候老师下一句就是答案（“我们来看一个例子”“所以结论是……”）。
- 不知道整部视频讲了什么：这一句是在铺垫、下定义、举例还是总结，为哪个结论服务，前面有没有讲过这个词。

## 2. 思路：三层存储，四层上下文

```
存储（代理 data/memory/<视频>.json）          查询时拼进提示词（按暂停点 t）
L2 全局   主题 · 主线 · 3–10 章 · 术语表   →  ① 全局层  主线 + 章节大纲（标出“用户现在在这一章”）+ 术语
L1 小节   每 2–3 分钟一节：标题/摘要/术语   →  ② 章节层  当前小节和前后各一节的摘要
L0 原文   整片字幕 [from, to, text]          →  ③ 焦点层  t−30 ~ t+30 秒原文，▶ 标出暂停那一句，
                                                         分“暂停前，用户刚听过 / 暂停后，用户还没看到”
                                               →  ④ 回溯层  焦点里的术语在前文第一次出现的原文；
                                                         有问题时再按问题检索焦点之外最相关的一节
```

粗的层只给方向，细的层才是解释对象。提示词里写明：解释对象永远是焦点层 ▶ 那句；全局层、章节层是摘要，只用来判断“老师此刻在干什么”，不能当原话引用，也不要复述大纲；“暂停后”的字幕帮助看懂意图，但不能当成用户已经听过。

## 3. 字幕从哪来

**首选：完整字幕，和 v1.3 课程重点共用一份**（`state.kp.track`，见 [v1.3 方案](v1.3-方案.md) 2.2）。内容脚本带用户自己的 B 站登录态读：

```
x/web-interface/view?bvid=…        → 各分P 的 cid、时长、简介（v1.4 多取了简介，给 map / reduce 当背景）
x/player/v2?bvid=…&cid=…           → subtitle.subtitles[{lan, lan_doc, subtitle_url}]（失败再试 x/player/wbi/v2）
subtitle_url（aisubtitle.hdslb.com）→ {body: [{from, to, content}]}
```

- 选字幕、校验（行数、时长、和播放器上实际出现的字幕比对）都沿用 v1.3；AI 字幕要登录才有。
- **什么时候交给代理**：完整字幕读到后，本视频播放满 10 秒（和课程重点同一个门槛，点开看一眼的视频不花调用），或第一次求助时。播放器上正显示字幕、还没比对过时，先等攒够 3 句确认是这个视频的。
- **事后发现串台**（比对失败，v1.3 会丢掉完整字幕）：之后用播过的字幕做记忆时带 `force`，把代理里那份整个重做。
- 设置页「读取完整字幕」现在课程重点和整片记忆都用：关掉课程重点也照读，只有关掉这一项才不读。

**退路：边播边记**。读不到完整字幕（没字幕、要登录、番剧页、设置里关了）时，求助前把已经播过的字幕发给代理（≥30 句才发，之后每多 40 句重发一次），记成 `source: "live"`。完整字幕优先：已有整片记忆时忽略边播边记；边播边记的记忆正在生成时来了完整字幕，直接换掉。

## 4. 生成（代理，后台异步）

- **切小节**（不调模型）：默认每节约 150 秒或 900 字，在停顿（相邻字幕间隔 ≥0.6 秒）或句末处切；没有合适的切点时最长到 1.6 倍硬切。最后一节不到目标的 40% 时并进前一节。每节原文每 30 秒插一个 `[mm:ss]`。
- **map**（`prompts/memory_map.md`）：一批最多 8 节、6000 字，返回每节 `title ≤12 字 / summary ≤60 字 / terms 0–5 个原词`。默认最多 3 批并行。
- **reduce**（`prompts/memory_reduce.md`）：读全部小节摘要，返回 `topic / summary ≤150 字（写出步骤间的逻辑）/ chapters 3–10 章 / terms ≤12 个`。代理会修正章节，保证按顺序覆盖全部小节、不重叠。
- 都是 JSON 模式、temperature 0.2；上游不支持 JSON 模式（HTTP 400）就去掉重试；每批最多试 2 次；401/403 直接放弃。
- **不阻塞**：代理是单线程的，生成要调几次模型（真模型十几秒到一分钟）。所以用异步 `HttpClient` 任务，主循环每 250ms、以及每处理完一个请求时推进一次。生成期间 `/explain`、`/followup` 照常响应：焦点层、回溯层不需要模型，立即可用；没生成完的小节在章节层里写“摘要还没生成，原文开头……”。
- **复用**：记忆按“字幕原文 + 切分参数”算 hash。同一份字幕已生成好就直接返回；字幕变了（边播边记变多了、换成整片字幕）只重做原文变了的小节。
- **状态**：`building` → `ready`（全部成功）/ `partial`（部分小节或大纲失败，能用的照用）/ `raw`（没配 Key：只存原文，焦点层和回溯层照样能用）。代理重启时遗留的 `building` 记为 `partial`。

## 5. 查询（每次求助 / 追问）

扩展在 `/explain`、`/followup` 里多带一个 `t_sec`（暂停点秒数）。代理按它拼四层（长度上限：全局 1600 字、章节 700 字、回溯 600 字；焦点按秒数截）。

- **焦点层替换规则**：记忆切出来的焦点原文不少于扩展送来字幕的 80% 时用记忆版（多了暂停后 30 秒和 ▶ 标记），否则用扩展送来的（例如这段字幕来自画面识字）。
- **回溯层**：① 焦点和问题里出现的术语（来自术语表和小节 terms，长词优先），在焦点之前第一次出现的位置，给前后各一句原文，最多 2 条；② 有具体问题时（不是默认的“这里没听懂”），用二字词 + 逆文档频率在焦点以外的小节里检索，至少命中 2 个二字词才算，给这一节的摘要和命中最多的那句原文。
- **防串台**：扩展送来的字幕和记忆里同一时间段的字幕二字词重合不到 30% 时，这次不用记忆（`memory_status: "mismatch"`），比如同一个编号换了视频。
- 没有记忆时各层填说明文字（全局层写“没有整片字幕记忆，只拿到了暂停点附近的字幕”），提示词里不会留下 `{{占位符}}`，行为和 v1.2 一样。

## 7. 接口与配置

| 接口 | 说明 |
|---|---|
| `POST /memory/build` | `{video_id, subject, desc, source: "bilibili"\|"live", lan, duration, cues: [[from, to, text], …], force?}`，立即返回状态，生成在后台进行。也接受 B 站原始格式 `[{from, to, content}]` |
| `GET /memory/status?video_id=` | `status / source / cues / chunks / chunks_llm / chapters / topic / progress / error / built_ms` |
| `POST /memory/context` | 调试用：`{video_id, t, question?, transcript?}` → 实际会拼进提示词的四层 |
| `/explain`、`/followup` | 请求多一个 `t_sec`；`/explain` 响应多一个 `memory: {used, status, focus, chapters, chapter, recall_hits}`，抽屉底部显示“整片记忆 · 4 章「当前章名」”或“整片记忆生成中” |
| `/health` | `features` 多一个 `memory`；多一个 `memory: {enabled, building: [正在生成的视频]}` |

`config.json` 可选 `memory` 段（都有默认值，不写也行）：

```json
"memory": { "enabled": true, "chunkSec": 150, "chunkChars": 900, "focusBefore": 30, "focusAfter": 30, "parallel": 3 }
```

日志：生成完写一行 `type: "memory"`（小节数、模型摘要数、章节数、调用次数、耗时）；`call2` / `call3` 多 `t_sec`、`memory_status`、`memory_focus`、`memory_chapter`、`memory_layer_chars`、`recall_hits`、`prompt_transcript`（用了记忆版焦点时）；完整字幕拿没拿到、为什么，看 v1.3 的 `client_event / kp_track`。

## 8. 成本粗估

以 30 分钟、约 9000 字字幕的课为例：12 个小节 → map 2 批 + reduce 1 次，共 3 次调用，输入约 1 万字、输出约 2500 字，只在第一次打开这个视频时花一次（结果存盘，换小节参数才会重做）。之后每次求助的提示词多 1500–3000 字（全局层 + 章节层 + 回溯层 + 暂停后 30 秒）。

## 9. 自测（模拟上游，不花钱）

- `dev/sample-subtitles.json`：合成的约 8 分钟线性代数课（98 句，B 站字幕格式），讲线性组合 → 定义 → 用秩判定 → 例题 → 几何意义 → 小结。
- `dev/test-page.html?full=1`：换成这节课，并自动带上 `?bvid=BV1full&track=1`，字幕走模拟页的仿 B 站字幕接口（v1.3），课程重点和整片记忆用同一份。
- `dev/mock-upstream.js` 能回 map / reduce（按原文里出现的术语拼摘要和章节）；`GET /__last?kind=call2` 看某类调用最后一次的请求体。
- `dev/mock-config.json` 把小节切细（40 秒 / 180 字），8 分钟的样例能切出 8 节。

已验证：

1. 页面一打开就取到整片字幕并生成记忆（模拟上游约 2.5 秒，8 节 → 4 章）。
2. 直接跳到 04:10、一秒没播就求助：Call 2 收到四层；焦点层含暂停后 30 秒；▶ 标在 04:06 那句；回溯层找到“初等行变换”在 03:22 第一次出现。
3. 追问“几何上三个向量线性相关是什么样子”：回溯层检索到焦点之外“我们再从几何上看一下线性相关”那段；Call 1 收到章节大纲。
4. 边播边记 40 句 → 80 句 → 整片字幕：分别 3 → 6（沿用 2）→ 8（沿用 5）个小节；已有整片记忆时边播边记被忽略。
5. 生成中途求助：章节层显示“摘要还没生成，原文开头”，解释照常返回。上游拒绝 JSON 模式：去掉后重试成功。
6. 字幕和记忆对不上（拿一段做菜的字幕去问）：这次不用记忆。所有提示词都没有残留 `{{占位符}}`。

以上 1–6 是合并前（自己取字幕的版本）验证的；合并到 v1.3 之后（改用 `kp.track`）在模拟页上重新走了一遍，结果见 CHANGELOG。

**没验证**：真模型下摘要和章节的质量、四层上下文是否真的让解释更准（需要拿真实课程 A/B 比较）；真实 B 站页面上走查（v1.3 已经在 B 站页面上核对过字幕接口能带登录态返回）。

## 10. 已知限制和下一步

- 番剧/课程页（`/bangumi/play/ep…`、`/cheese/play/…`）读不到完整字幕，走边播边记退路（和 v1.3 课程重点一样）。
- 课程重点（Call 5）和整片记忆各读一遍完整字幕、各调各的模型；以后可以让课程重点直接用记忆里的小节摘要，或反过来。
- 小节切点靠停顿和句末；AI 字幕没有标点、停顿也不明显时，会多是硬切。
- 回溯检索是二字词 + 逆文档频率，同义改写（“共面” vs “在一个平面里”）找不到；可以考虑让 map 多产出同义词，或者用向量检索。
- `data/memory/` 不会自动清理（一节 30 分钟的课约几十 KB）。
- 历史节点回溯时用的是节点里的 `t`，记忆会照常拼上；节点本身不存记忆。
- 下一步建议：先拿 3–5 个真实课程，用真模型对比“有/没有整片记忆”的解释质量和追问命中，再决定是否合并。
